# 多话题分答（astrbot_plugin_multi_topic）

让 AI 在你**连着发来几条消息 / 一条消息里有几个话题**时，引用原消息、分条逐一回复，
像真人聊天一样接话，而不是只回答最后一句。

适配 NapCat / OneBot v11（`aiocqhttp`）接入的 QQ。

---

## 效果

以前：

> 你：你下午吃了什么？
> 你：你晚上想干点啥？
> AI：晚上打算出去走走。

现在（两条回复都会出现，各自引用对应原消息，每条再拆成几段短句）：

> **AI**（引用「你下午吃了什么？」）：刚吃了碗牛肉面  
> **AI**：有点咸，不过汤还挺好喝
>
> **AI**（引用「你晚上想干点啥？」）：晚上啊，可能出去走走  
> **AI**：也说不定就在家躺着看剧

没有 `1. 2. 3.`，没有“关于第一个问题”，就是正常的 QQ 聊天。

---

## 为什么之前只回答最后一条

AstrBot 有一个 follow-up 机制：当第一条消息正在生成回复时，你紧接着发的第二条会被
并进**同一次**生成。模型看到两条消息后，往往只回应最新那条，第一条就被吞掉了。

本插件在消息进入大模型之前先把短时间内的连续消息收进「待回复队列」，等你想发的都发完，
再一起交给模型按话题回复，因此不会再出现“只答最后一条”。

## 安装

WebUI →「插件」→「安装插件」→ 上传 `astrbot_plugin_multi_topic.zip` → 确认启用。

无第三方依赖。

## 工作流程

1. **收集**：每条消息先进入该会话的待回复队列；等 `merge_window_seconds` 秒，
   看是否还有后续消息（已经攒到两条时会缩短等待）。
2. **分话题**：队列里的每条消息是一个话题；如果一条消息里本身有多个问句，也会拆开。
   「嗯」「然后呢」这类短句会并回上一个话题，不会单独开一条回复。
3. **注入格式要求**：在 `on_llm_request` 里告诉模型“有 N 条消息要按顺序回”，
   要求它用内部分隔符输出、口语化、不要编号。
4. **拆条 + 引用发送**：在 `on_decorating_result` 里把模型输出拆成多条 QQ 消息；
   每个话题的第一条引用对应原消息，然后按 `segment_delay` / `topic_delay` 逐条发出。
5. **清理**：把只用于分条的分隔符从历史记录里去掉，避免污染后续上下文。

## 配置说明

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 总开关 |
| `merge_window_seconds` | `2.5` | 连续消息合并窗口。两条消息间隔小于它就会被合并；设为 `0` 关闭合并 |
| `debounce_max_chars` | `80` | 超过这个长度的消息不等待，直接回复 |
| `pending_ttl` | `120` | 待回复消息最多保留多久 |
| `max_topics` | `6` | 单轮最多处理几个话题 |
| `min_topic_chars` | `2` | 话题最短长度 |
| `continuation_max_chars` | `6` | 多短的句子算“接着上一个话题说” |
| `send_quotes` | `true` | 回复时引用原消息 |
| `segment_delay` | `0.5` | 同一话题内多条消息的间隔（秒） |
| `topic_delay` | `0.8` | 不同话题之间的间隔（秒） |
| `max_segment_chars` | `120` | 单条回复最长多少字，超过会按标点拆开 |
| `streaming_guard` | `true` | 检测到流式输出时跳过分条，避免标记泄露 |
| `command_prefixes` | `["/","／","!","！","#"]` | 这些开头的消息按指令处理，不参与合并 |
| `debug` | `false` | 输出调试日志 |

### 怎么调

- **觉得回复变慢**：`merge_window_seconds` 调到 `1.5~2.0`；如果你的两条消息间隔更长，
  就需要相应调大，否则第二条会落在第一条的生成过程中。
- **不想每条都等**：设成 `0`，就只处理「一条消息里多个话题」，不再合并连续消息。
- **觉得引用太多**：`send_quotes` 关掉。
- **回复太碎**：把 `max_segment_chars` 调大，或让模型一个话题只回一条（改人设提示即可）。

## 与其他插件协同

- **分段回复类插件**：本插件在需要分话题时自己拆条发送，并清空原结果，
  不会和分段插件重复发送；普通单话题回复仍走 AstrBot 原生流程，分段插件照常工作。
- **表情包插件**：在 `on_decorating_result` 阶段、优先级高于本插件时加入的表情包内容
  会保留在消息链里；如果出现非文本内容，本插件会放弃拆条、交回原生流程。
- **主动消息 / 定时任务插件**：不经过这条链路，不受影响。
- **TTS**：分话题回复由本插件直接发送，**不会经过 TTS**；普通回复仍然会。
- **人设 / 记忆插件**：模型调用仍是 AstrBot 原生链路，人设、上下文、工具都保留。

## 常见问题

**Q：为什么第一条消息要等 2.5 秒？**
A：为了等你把第二条发完。已经收到第二条时会立刻缩短等待。可以把 `merge_window_seconds` 调小，
但要大于你两条消息的实际间隔。

**Q：回复没有引用？**
A：确认 `send_quotes` 开着；另外只有“多个话题”时才会引用，单话题回复走原生流程，
引用与否取决于 AstrBot 自己的「引用回复」设置。

**Q：回复里出现了 `[[T1]]`，而且是一条条零散发出来的？**
A：这是**流式输出**造成的，不是别的插件。QQ 不支持原生流式，当
`streaming_response` 和 `streaming_segmented` 都开启时，AstrBot 会在模型生成过程中
按句子/换行把原文逐条发出去，`[[T1]]`、`[[S]]` 也就各自成了一条消息；等插件拿到完整
文本时已经晚了。

解决办法：在 `配置文件 → AI`（找不到时可在该配置的 JSON 里改）关闭「流式输出」和
「流式分段」，也就是：

```json
"provider_settings": {
  "streaming_response": false,
  "streaming_segmented": false
}
```

本插件检测到这两项都开着时会**主动跳过分条**并在日志里警告，避免再出现标记泄露。

**Q：群聊里会触发吗？**
A：只有 @ 机器人 / 唤醒词触发的消息才会进入处理流程。

**Q：图片、语音消息会合并吗？**
A：不会，含多媒体内容的消息直接走原生流程。

## 查看日志

打开插件配置里的 `debug` 后，关键步骤会以 **INFO** 级别输出（不需要把全局日志级别调到 DEBUG）：

```text
[INFO] [Plug] [multi_topic] 又收到新消息，本条并入下一批: ...
[INFO] [Plug] [multi_topic] 待回复 2 个话题: ['你下午吃了什么？', '你晚上想干点啥？']
[INFO] [Plug] [multi_topic] 已向请求注入 2 个话题的分答提示
[INFO] [Plug] [multi_topic] 已按 2 个话题分条发送 3 条消息
```

在哪里看：

- **WebUI**：左侧「数据与日志」→「日志」，在过滤器里选「来源 = 插件」「插件 = 多话题分答」，
  也可以直接搜 `multi_topic`。
- **控制台**：桌面端 / 启动器窗口，或 `docker logs -f <容器名>`。
- **文件日志**：`系统设置 → 常规 → 日志` 开启文件日志后，写入 `data/logs/astrbot.log`。
- 如果想看插件不开 `debug` 时的底层 `DEBUG` 行：`系统设置 → 常规 → 日志 → 控制台日志级别` 调成 `DEBUG`。

## 已知限制

- 仅对 `aiocqhttp`（NapCat / OneBot v11）生效；
- 依赖 AstrBot 的 `on_llm_request` / `on_decorating_result` / `on_agent_done` 钩子；
- 分话题回复由插件直接发送，会绕过 AstrBot 的 TTS、长消息转转发、内置分段回复等后处理；
- 如果两条消息间隔超过 `merge_window_seconds`，第二条仍可能被 AstrBot 的 follow-up 机制合并；
- 仅支持纯文本消息链；带图片/语音的回复会交回原生流程。
